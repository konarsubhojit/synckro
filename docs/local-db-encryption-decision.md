# Local database encryption: field-level vs whole-database

Status: **Decided** — design-only task (E5.S1.T1). No code changes in this task;
this document records the approach the follow-up implementation task should use.

## Context

Synckro persists sync-pair configuration, provider account metadata, local/remote
file indexes, pending-upload queues, and structured sync logs in a Room/SQLite
database (`SynckroDatabase`, see `app/src/main/java/com/synckro/data/local/db/`
and `entity/Entities.kt`). OAuth tokens and other secrets are **not** stored in
this database today — `GoogleDriveAuthManager.kt` and `OneDriveAuthManager.kt`
already persist account credentials separately via `MasterKey` +
`EncryptedSharedPreferences` (`androidx.security.crypto`).

The remaining sensitive-ish data living in Room is mostly metadata: account
`email`/`displayName`, local `content://` tree URIs, relative file paths, and
provider delta/claim tokens (`AccountEntity`, `SyncPairEntity`,
`LocalIndexEntity`, `FileIndexEntity`, `PendingUploadEntity`,
`PairRunLeaseEntity`). This task evaluates how to encrypt that data at rest.

## Options evaluated

### Option A — Field-level encryption via Room `@TypeConverter`

Reuse the existing `MasterKey`/Tink-backed AEAD primitives already wired up in
`GoogleDriveAuthManager`/`OneDriveAuthManager`, and add Room `@TypeConverter`s
that encrypt/decrypt individual sensitive `String` columns (e.g. `email`,
`localTreeUri`, path fields) transparently on read/write, storing ciphertext
(Base64/BLOB) in otherwise-unchanged SQLite columns.

**Pros**
- Reuses primitives and key material already vetted in the auth managers — no
  new crypto library or NDK/JNI surface.
- No change to APK size beyond the `androidx.security.crypto` dependency
  already present.
- Selective: only columns that actually need confidentiality are encrypted;
  everything else (ids, timestamps, enums, counters) stays plaintext and
  remains indexable/sortable/queryable with `WHERE`/`ORDER BY` in SQL.
- Migration is additive: existing Room `Migration` objects can convert
  specific columns in place; schema/version bump is small and scoped per
  table, not a full-database rewrite.
- Debuggability preserved: non-sensitive columns remain human-readable when
  inspecting the DB file during development.

**Cons**
- Encrypted columns lose SQL query-ability (`LIKE`, range filters, joins on
  that column) since ciphertext is non-deterministic (AEAD nonce per value);
  any lookups on those fields must happen in Kotlin after decryption, or via a
  separate deterministic-hash index column.
- Encryption is opt-in per field — a developer adding a new sensitive column
  later must remember to route it through the converter; nothing enforces it
  at the schema level.
- Row-by-row overhead (key unwrap + AEAD encrypt/decrypt per field per query)
  is not free, though for our table sizes (tens–thousands of rows, not
  millions) this is expected to be negligible.

### Option B — Whole-database encryption via SQLCipher for Android

Replace the stock SQLite/Room driver with `net.zetetic:android-database-sqlcipher`,
encrypting the entire `.db` file with a single passphrase derived from Android
Keystore-backed material.

**Pros**
- Encrypts everything uniformly, including indexes, rowids, and any future
  columns, without per-field opt-in.
- Well-established library with its own migration/versioning story for the
  encrypted file itself.

**Cons**
- Significant APK size increase: SQLCipher ships native `.so` binaries for
  every ABI (arm64-v8a, armeabi-v7a, x86, x86_64), commonly adding several MB
  to the app compared to the field-level approach's pure-JVM/Tink code path.
- Requires swapping Room's `SupportSQLiteOpenHelper.Factory` for
  `SupportFactory` from SQLCipher and managing the passphrase lifecycle
  (Keystore-wrapped, supplied at DB-open time) — a larger, riskier migration
  than adding `TypeConverter`s, and it touches every table at once instead of
  incrementally.
- All columns become equally opaque, including ones that don't need it
  (autogenerated ids, enums, counters used in `WHERE`/`ORDER BY` clauses,
  e.g. `PendingUploadEntity` status filtering, `FileIndexEntity` scans) —
  SQLCipher decrypts pages transparently so in-DB queries still work, but at
  the cost of decrypting/re-encrypting far more data per operation than is
  actually sensitive.
- Duplicates capability we already have: we would end up depending on two
  different crypto stacks (`androidx.security.crypto`/Tink for auth manager
  secrets, plus SQLCipher/OpenSSL for the DB), increasing maintenance and
  audit surface instead of reusing one.
- Testing impact: unit tests running on the JVM (Robolectric/local SQLite)
  need the SQLCipher native library or a test double, adding CI complexity
  compared to pure-Kotlin `TypeConverter`s that work unmodified under JVM
  tests.

## Decision

**Field-level encryption via Room `@TypeConverter`s reusing the existing
`MasterKey`/`androidx.security.crypto` primitives (Option A)** is the approach
the next implementation task should build on.

Rationale: the amount of genuinely sensitive data in the local database is
small and identifiable (account email/display name, local tree URI, relative
paths, provider tokens if ever cached in Room), the existing auth managers
already establish the key-management pattern to reuse, and the incremental,
per-column migration path is far lower risk than swapping the entire
Room/SQLite driver for SQLCipher. The APK-size and native-dependency cost of
SQLCipher is not justified given the size and query patterns of this
database, and whole-DB encryption would make plain SQL filtering/sorting on
non-sensitive columns unnecessarily opaque.

## Notes for the implementation task

- Add `Converters` functions (e.g. `encryptedString`/`decryptedString`) backed
  by a `MasterKey`-derived AEAD, mirroring the key alias conventions already
  used in `GoogleDriveAuthManager.kt`/`OneDriveAuthManager.kt`.
- Start with `AccountEntity.email`, `AccountEntity.displayName`, and
  `SyncPairEntity.localTreeUri` as the first candidates; expand only as new
  genuinely sensitive fields are added.
- Any column that needs equality lookups after encryption (e.g. matching a
  `localTreeUri`) should keep a deterministic hash column alongside the
  ciphertext, rather than relying on SQL `WHERE` against non-deterministic
  ciphertext.
- Bump the Room schema version and provide an explicit `Migration` that
  re-encrypts existing plaintext values in place.
